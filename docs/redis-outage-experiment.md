# Disposable Redis-outage diagnostic

This is an opt-in, non-required GitHub Actions experiment, not a CI flake fix. The separate `redis-outage-experiment.yml` workflow runs only on a same-repository PR into `main` whose branch begins `experiment/redis-outage-kind-` and changes the experiment workflow, driver or tests. It does not change the required `check` and two `Compatibility` contexts, strict smoke assertions, or the release gate. It never runs on `main` push and has no release job. Do not use it against a shared cluster.

The job creates its own kind cluster and dedicated kubeconfig on a GitHub-hosted runner, installs pinned Argo CD v3.4.7 and Argo Workflows v3.7.4, and syncs the existing `test/e2e/argocd-application.yaml` fixture from the exact PR head. The driver checks runner identity, kubeconfig path, the only kind cluster/context, and a loopback Kubernetes API before applying the fixture or touching Redis. It waits for the fixture Workflow to succeed, then gets an admin API session locally without printing the credential. It opens independent service and server-pod port-forwards on loopback.

Each phase emits a fixed-schema Redis readiness/endpoints record and GET results for the fixture Workflow resource, application tree and `/healthz?full=true` control through both forwards. Baseline requires healthy responses. The driver scales only `argocd/argocd-redis` to zero in that verified cluster, waits for zero ready replicas/endpoints, records the outage probes (including bounded timeouts), then scales back to one and requires healthy recovery. An attempted injection triggers restoration even when a probe or Kubernetes command fails; an additional unconditional workflow cleanup step restores Redis if the driver is cancelled or killed. Setup/probe/injection/restore failures make the experimental job red. The job and steps have explicit deadlines; a cancelled job cannot guarantee cleanup, but its whole cluster is disposable with the runner.

Output contains only allowlisted phase, source and route templates, status class/timeout, capped duration, and capped aggregate Redis readiness/endpoint counts. No raw URL/query, response body, HTTP header, credential, pod identifier, Kubernetes error, or pod log is printed. A reproduced stall would show Redis unavailability is sufficient in this setup, **not** that Redis caused the historical failure, why Redis became unready there, or that the flake is fixed. Compare with the preserved failed v3.4.7 job separately; do not merge or relax the strict smoke based on a green experiment.
